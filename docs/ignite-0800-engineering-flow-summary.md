# Ignite 0800 工程流总结

> 用途：把 `0800` 的实验室模式，从“会审 PR”进一步落成一条维护者和协作者都能执行的工程流。  
> 适用范围：外部 PR、实验分支、专题分支、Server 最小接线验证，以及进入 `0900` 前的吸收判断。  
> 原则：先隔离、再验证、后吸收，不让实验流直接污染稳定线。

---

## 1. 一句话定义

`0800` 的工程流不是“欢迎大家提 PR”，而是：

**把外部改动放进可治理的容器里，跑完分流、验证、回收、裁决四段流程，再决定它是否值得进入推荐路径。**

---

## 2. 0800 要解决的现实问题

进入 `0800` 后，Ignite 面对的不再只是内部路线图，而是下面这类现实输入：

- 外部贡献想试传输层、Server 接线或中间件改动
- 不同人会同时带来不同成熟度的实验思路
- 有些 PR 值得继续孵化，有些只适合短期专题验证
- 维护者必须保护稳定线的发布节奏

所以 `0800` 需要的不是更宽松，而是更清楚的工程流。

---

## 3. 推荐总流程

建议所有进入 `0800` 的改动都按下面七步走：

1. 入口登记
2. 分流判级
3. 分支落位
4. 最小验证
5. 回归与观测补齐
6. 回收或继续孵化
7. 提交 `0900` 裁决候选

这七步里，任何一步没站稳，都不应越级进入稳定推荐路径。

---

## 4. Step 1：入口登记

任何外部改动进入实验室模式前，至少要登记四件事：

- 想解决什么问题
- 影响哪一层
- 是否改变公开 API 或默认行为
- 计划如何验证

推荐按影响层先归类：

- 文档 / 样例
- Client / transport
- Server / engine
- TLS / crypto / compatibility
- benchmark / governance / tooling

如果连问题定义都没有，直接停在讨论，不进入工程流。

---

## 5. Step 2：分流判级

维护者收到输入后，先不要急着看实现，先判断它属于哪一类：

### A. 稳定补丁

特征：

- 低风险
- 不改默认路径
- 不引入新抽象

去向：

- 可直接走稳定线或文档修复线

### B. 实验改动

特征：

- 影响共享传输抽象、socket Client、Server 接线、替代引擎
- 可能改动默认语义或长期架构边界

去向：

- 进入实验线

### C. 专题验证

特征：

- 只验证单一主题
- 生命周期短
- 目标明确

去向：

- 进入专题线

如果一项改动同时想改三件事，先拆单，不要让工程流从入口就失真。

---

## 6. Step 3：分支落位

### 稳定线

只接：

- 文档修复
- 样例修复
- 低风险 bugfix
- 已在实验线完成验证的回收提交

### 实验线

优先接：

- 共享传输抽象
- socket Client 深化
- `ig/net` / 替代引擎 / Server 最小接线
- 需要较长观察期的行为改动

### 专题线

优先接：

- TLS / `jinkuiSSL`
- prefork / reuseport
- benchmark 基线
- 特定平台或契约验证

分支一旦落位，就不要在验证中途随意改口径。

---

## 7. Step 4：最小验证

每条进入 `0800` 的线，先做“最小可解释验证”，不是一上来追完整功能。

最低要求至少包括：

- 能说明最小接入面是什么
- 能说明哪些行为保持不变
- 能说明失败时如何回退
- 能说明当前不支持什么

对于 Server 接线类改动，最低要回答：

- 是否只是最小接入验证
- 是否复用了现有语义
- 是否会影响默认 Server 路径

---

## 8. Step 5：回归与观测补齐

一旦最小验证成立，就不能停在“能跑 demo”。

至少要继续补：

- 成功路径回归
- 失败路径回归
- 错误可观测字段
- 迁移或兼容说明
- 基准或维护成本留痕

判断标准不是“代码多漂亮”，而是：

- 后面的人能不能复验
- 出问题时能不能定位
- 维护者敢不敢继续让它活在实验体系里

---

## 9. Step 6：回收、冻结、继续孵化

验证完后，每条线只能走三个方向之一：

### A. 回收进稳定线

条件：

- 风险已明显降低
- 文档与回归齐套
- 不破坏发布节奏

### B. 继续留在实验线

条件：

- 方向有价值
- 但语义、维护成本或兼容边界还没稳

### C. 归档或关闭

条件：

- 问题定义不成立
- 收益不足以支撑维护成本
- 无法给出清楚回退路径

实验室模式的成熟度，体现在“敢关闭无效实验”，不是“什么都永远留着”。

---

## 10. Step 7：进入 0900 裁决候选

只有满足下面几类材料，才建议把某条实验成果推给 `0900`：

- 一份问题定义与目标边界
- 一份验证结论
- 一份回归 / 基准 / 观测留痕
- 一份迁移或兼容说明
- 一份维护成本判断

`0900` 不是重新帮 `0800` 做工程整理，而是基于已整理好的材料做裁决。

---

## 11. 维护者每天实际怎么用这份工程流

如果到了 `0800`，维护者日常可以按下面顺序工作：

1. 先看入口登记是否清楚
2. 再判断该进稳定线、实验线还是专题线
3. 再检查是否已有最小验证与回退说明
4. 再判断是否值得继续投入回归与观测
5. 最后决定：回收、续养、归档

这能把“拍脑袋评审”尽量变成“有节奏的实验治理”。

---

## 12. 与 0500 / 0600 / 0700 的关系

- `0500`：解决主线可信发布
- `0600`：建立共享传输抽象与本地生产级闭环
- `0700`：形成多分支常态化治理
- `0800`：让外部输入进入可治理工程流
- `0900`：做统一裁决

换句话说，`0800` 不是重新发明路线图，而是把前面三阶段的内部治理能力，转成可承接外部输入的工程机制。

---

## 13. 当前结论

如果没有这条工程流，`0800` 很容易变成“开门迎客但没人知道怎么收场”。  
有了这条工程流，实验室模式才真正有资格面对外部贡献和 Server 接线验证。
