# Ignite 0.8.2 Preview API 增量参考

本页只列 0800 新增或行为发生重要变化的公开接口。0700 延续接口仍见 [`api.md`](api.md)。

## Ctx：请求体流

```cangjie
public func requestBody(): InputStream
public func requestJsonReader(): JsonReader
public func saveBodyToFile(destPath: String): Int64
```

- `requestBody()` 使用 `Config.bodyLimit` 限制累计读取量。
- 超限抛出 `BufferedRequestBodyTooLargeException`。
- `requestJsonReader()` 直接从请求流读取 JSON token，不先构造完整 `String`。
- `saveBodyToFile()` 优先复用已缓存 body，否则直接从流写入目标文件。
- 如果流路径已经先消费，后续 `bodyBytes()` / `bodyString()` 只会看到未读部分；不要混用两种消费模型。

## Ctx：通用响应流

```cangjie
public func sendStream(
    stream: InputStream,
    contentType!: String = "application/octet-stream",
    contentLength!: ?Int64 = None
): Ctx
```

- 已知长度时设置 `Content-Length`。
- 未知长度的 HTTP/1.x 响应使用 chunked。
- HTTP/2 不写入 `Transfer-Encoding`。
- `HEAD` 请求不会发送 body。
- 如果压缩中间件注册了可接受的流式压缩计划，`sendStream` 会包装输入流并移除原长度。

## Ctx：流式 JSON

```cangjie
public func jsonWrite(writerFn: (JsonWriter) -> Unit): Ctx

public func jsonStream(
    writerFn: (JsonWriter) -> Unit,
    contentLength!: ?Int64 = None
): Ctx

public func jsonSerializeStream<T>(
    obj: T,
    contentLength!: ?Int64 = None
): Ctx where T <: JsonSerializable

public func jsonEncodeStream(
    obj: JsonWriterEncodable,
    contentLength!: ?Int64 = None
): Ctx

public func jsonSeaStream(
    writerFn: (SeaJsonWriter) -> Unit,
    contentLength!: ?Int64 = None,
    bufferLimit!: Int64 = 8192
): Ctx
```

### 如何选择

| API | 适合场景 | 关键差异 |
| --- | --- | --- |
| `jsonWrite` | 直接使用 stdx `JsonWriter` 回调 | H1 无压缩时直接写 transport writer；H2 通过有界 `JsonWriterInputStream` 接入增量 DATA 流。 |
| `jsonStream` | 需要 stdx `JsonWriter`，同时希望复用 `sendStream` | 通过 `JsonWriterInputStream` 桥接。 |
| `jsonSerializeStream` | 类型实现了 `JsonSerializable` | 不经过 `serializeJson(...) -> String`。 |
| `jsonEncodeStream` | 类型实现了 `JsonWriterEncodable` | 不读取 `Config.jsonEncoder`，wire shape 由类型自行提供。 |
| `jsonSeaStream` | 新代码、大数组、持续生成数据 | 使用 SeaJson writer 和有界缓冲桥，默认上限 8192 bytes。 |

共同限制：这些接口不会设置完整 `ctx.responseBody`。依赖 buffered response 的 `etag`、cache、idempotency 等中间件，不应被视为自动兼容。

示例：

```cangjie
app.get("/events", { ctx =>
    ctx.jsonSeaStream({ writer =>
        writer.beginArray()
        for (i in 0..1000) {
            writer.value(i)
        }
        writer.endArray()
    })
})
```

## Ctx：低层 writer 与长连接

```cangjie
public func transportWriter(): ResponseTransportWriter
public func transportOutputStream(): ResponseTransportOutputStream
public func writer(): ResponseWriter
public func sse(): SseWriter
```

`transportWriter()` 不修改 framing header。直接使用它时，调用方必须自行设置状态码、`Content-Type`、`Content-Length` 或 chunked 语义。常规流式响应优先使用 `sendStream()`。

0800 的 Ignite 自有 writer 提供统一的 `flush()` / `close()` 生命周期：

- `ResponseTransportOutputStream`、`ResponseWriter` 与 `SseWriter` 可显式
  flush 和 close；
- `close()` 只终结当前响应写入面，并拒绝后续写入，不会关闭底层 HTTP
  连接；重复 close 是幂等的；
- `flush()` 会转发给支持 lifecycle 的后端，但不承诺所有后端都能在
  handler 返回前强制完成 wire drain。Native H1/H2 carrier 与 stdx
  compatibility backend 仍受各自提交边界约束；需要真实流控与有界传输时
  继续优先使用 `sendStream()` 或已标明的 bounded streaming API。

## Ctx：静态预压缩文件

```cangjie
public func sendPrecompressedFile(
    encodedPath: String,
    originalPath: String,
    encoding: String
): Ctx
```

它发送预先生成的压缩文件，同时按 `originalPath` 保留原资源 MIME，并设置 `Content-Encoding`、`Vary: Accept-Encoding`。Range 不应套用压缩副本。

## compressMiddleware：Ignite 自有 gzip/deflate 与 Zstd/Brotli baseline

`CompressConfig.level` 继续使用 `stdx.compress.zlib.CompressLevel`，以保持
0700 用户代码的源码兼容；该枚举现在只作为公开配置契约，由 Ignite 映射到
自有 codec，产品路径不再构造或执行 stdx zlib codec。`BestSpeed`、
`DefaultCompression`、`BestCompression` 当前分别映射为 native level
`1/6/9`。正数档位共享当前有界 fixed-Huffman/LZ 实现，不应把 level `9`
解读为已经提供独立的高压缩比策略。`gzip` 带 RFC 1952 header/trailer；
`deflate` 保持 Ignite 既有兼容行为，发送 raw DEFLATE。

动态 Zstd 与 Brotli 都是显式 opt-in：

```cangjie
app.use(compressMiddleware(config: CompressConfig(
    zstdEnabled: true,
    brotliEnabled: true,
    minBytes: 1024
)))

let buffered = compressZstdResponsePayload(bytes)
let streamed = ZstdCompressionInputStream(source, chunkSize: 16384)
let brotliBuffered = compressBrotliResponsePayload(bytes)
let brotliStreamed = BrotliCompressionInputStream(source, chunkSize: 16384)
```

中间件遵守 `Accept-Encoding` q-value；与 gzip/deflate 同权时保留原有
`preferGzip` 次序，只有 Zstd/Brotli 权重更高或其他 codec 被禁用时才选择
`zstd` / `br`。
frame 使用最大 `128 KiB` window/block，buffered frame 写入 content size，
stream frame 使用未知长度 header，两者默认带 XXH64 content checksum。
当前 encoder 只输出 RAW/RLE block：同值 run 会真实缩小，一般数据则依靠
`skipIfNoGain` 回退 identity。`CompressConfig.level` 暂不改变 Zstd 策略；
sequence/FSE/Huffman、字典与调优属于后续能力。

Brotli baseline 把输入拆成最大 `64 KiB` metablock。普通块以 RAW 形式保真，
同值块使用一个 literal 和 distance-one copy command 取得真实压缩收益；
buffered 路径可由 `skipIfNoGain` 回退 identity，stream 路径需要显式关闭该
选项后才会启用。通用 LZ、context modeling、多符号 Huffman、静态字典、
quality/window 调优和默认策略仍是后续能力。

## WebSocket 子协议

```cangjie
public func App.ws(path: String, subProtocols: Array<String>, handler: WsHandler): App
public func Group.ws(path: String, subProtocols: Array<String>, handler: WsHandler): Group
public func Ctx.upgradeWebSocketWithSubProtocols(subProtocols: Array<String>): WsConn
public func App.ws(path: String, options: WebSocketOptions, handler: WsHandler): App
public func Ctx.upgradeWebSocketWithOptions(options: WebSocketOptions): WsConn
```

`WebSocketOptions.maxIncomingMessageBytes` 默认是 `1 MiB`，用于约束单个完整
入站消息（包括分片重组后的总大小）。`WsConn` 允许一个活动 reader；并发
`writeText`、`writeBinary`、`ping` 和 `close` 会按完整帧串行化，不会把帧头
与另一个 payload 交叉写入。`WsConn.subProtocol` 返回最终协商结果，公开消息
类型为 `Text`、`Binary`、`Close`；Ping/Pong 在控制帧层自动处理。当前能力
属于 H1 upgrade；H2 extended CONNECT、permessage-deflate 和 Native WSS 不在
本轮承诺内。

## Config：body limit、timeout 与 backend

```cangjie
let config = Config(
    bodyLimit: 8 * 1024 * 1024,
    readTimeout: Duration.second * 30,
    writeTimeout: Duration.second * 30,
    serverBackendPolicy: ServerBackendPolicy.Stdx
)

config.readHeaderTimeout = Duration.second * 10
config.idleTimeout = Duration.second * 120
```

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `bodyLimit` | 4 MiB | 请求体流和 buffered body 的统一上限。 |
| `maxRequestBodySize` | 无独立字段 | 兼容构造参数别名，传入后写入 `bodyLimit`。 |
| `readTimeout` | 30 s | socket 读取阶段上限。 |
| `writeTimeout` | 30 s | socket 写入阶段上限；增大它不能修复 H2 flow-control 卡死。 |
| `readHeaderTimeout` | 10 s | 请求头读取上限；当前构造后赋值。 |
| `idleTimeout` | 120 s | keep-alive 空闲上限；当前构造后赋值。 |
| `serverBackendPolicy` | `ServerBackendPolicy.Auto` | 类型化选择 `Auto`、`NativeH1` 或 `Stdx`；优先级高于旧字符串 hint。 |
| `serverPreferredBackendHint` | 空字符串 | 明文为空时默认 native H1；`stdx-default` 显式回滚。 |
| `allowExperimentalServerBackend` | `false` | 允许实验 backend 参与选择，当前主要用于 native TLS 候选。 |
| `enableIoDriverRequestDiagnostics` | `false` | 默认只记录轻量 IoDriver 选择字段；开启后才构造每请求限制说明与事件列表。 |

`serverPreferredBackendHint` 继续作为兼容入口，但新代码优先使用
`serverBackendPolicy`。HTTPS 默认仍使用稳定 stdx TLS。不要把
`ServerBackendPolicy.NativeH1` 理解为已经稳定支持 native HTTPS；还必须显式允许
实验 backend，并承担 Preview 边界。

## Server runtime snapshot

```cangjie
let snapshot = app.serverRuntimeSnapshot()
println(snapshot.toJson())
```

`ServerRuntimeSnapshot` 暴露请求策略、最终 backend、选择原因、降级原因，以及
Native H1 的 accepted/active connection、active keep-alive、started/in-flight/
completed/rejected request 计数。当前计数范围仅为内置 cleartext Native H1；
`requestQueueDepth` 为 `0`，表示当前实现 accept 后直接 `spawn`，没有隐藏的框架
请求队列。stdx、TLS、自定义 engine 与 H2 不会借用这组计数冒充已覆盖。

## ignite.native_h2

最短可运行的 App Server 入口不是默认 `app.listen(...)`，而是显式安装
cleartext prior-knowledge engine：

```cangjie
import ignite.*
import ignite.native_h2.useExperimentalNativeH2ServerEngine

main() {
    let app = App()
    useExperimentalNativeH2ServerEngine(app)

    app.get("/", { ctx =>
        _ = ctx.sendString("hello from native h2")
    })

    app.listen("127.0.0.1", 3000)
}
```

使用 `curl --http2-prior-knowledge http://127.0.0.1:3000/` 或 `nghttp`
验证。这个 ServerEngine 不接受 TLS cert/key；浏览器 HTTPS 默认路径和 Native
H2 cleartext Preview 不是同一条 engine。完整选择说明见
[`h2-quickstart-0800.md`](h2-quickstart-0800.md)。

低层 socket API：

```cangjie
public func serveNativeH2SingleStream(socket: TcpSocket, handler: NativeH2SingleStreamHandler): Unit

public func serveNativeH2Connection(
    socket: TcpSocket,
    handler: NativeH2SingleStreamHandler,
    maxCompletedStreams!: Int64 = 0,
    control!: ?NativeH2ConnectionControl = None
): Unit

public func serveNativeH2SingleStreamApp(
    socket: TcpSocket,
    app: App,
    remoteAddress!: String = ""
): Unit

public func serveNativeH2AppConnection(
    socket: TcpSocket,
    app: App,
    remoteAddress!: String = "",
    maxCompletedStreams!: Int64 = 0,
    control!: ?NativeH2ConnectionControl = None
): Unit
```

Client：

```cangjie
let connection = NativeH2ClientConnection(socket)
let response = connection.send(request)
let responses = connection.sendBatch(requests)
connection.finish()

sendNativeH2SingleStreamRequest(socket, request)
sendNativeH2Requests(socket, requests)
```

`RestClient` 也提供一个显式 Preview 入口：

```cangjie
let client = RestClient(
    readTimeout: Duration.second * 15,
    writeTimeout: Duration.second * 15,
    poolSize: 10
)
    .allowExperimentalTransport()
    .preferTransportBackend("ignite-native-h2-client")

let response = client.get("http://127.0.0.1:8080/data")
let body = response.body()
client.close()
```

这个入口使用明文 HTTP/2 prior knowledge，不执行 H1 Upgrade，也不执行
TLS/ALPN。`RestClient` 负责同源连接池、connect/read/write timeout、状态码
重试、Cookie 和 observe 集成。只有完整消费 response body 的连接才会归池；
未读完即 `close()` 会发送 `RST_STREAM CANCEL`，并淘汰该物理连接。

当前请求 body 必须是 buffered/replayable 形式。每条池化连接最多持有一个
普通 `request().send()` 的公开 streamed response lease，因此它本身不是任意
多路并发 API。
配置 `onRequest` / `onRequestHook` 的 `HttpRequestBuilder` mutation hook 时，
当前 Native H2 backend 会拒绝发送，而不是假装完成等价改写。

需要一次显式、有界的多路请求时，可以使用 buffered batch Preview API：

```cangjie
let responses = client.sendNativeH2Batch([
    NativeH2BatchRequest("GET", "http://127.0.0.1:8080/a"),
    NativeH2BatchRequest("POST", "http://127.0.0.1:8080/b")
        .header("content-type", "text/plain")
        .bodyString("payload")
])
```

`sendNativeH2Batch(...)` 最多接受 32 个请求，全部 URL 必须在解析 `baseUrl`
后属于同一个 `http://` origin。请求使用递增奇数 stream ID 发出，响应按输入
顺序返回；服务端 handler 可以并行推进。实现会遵守对端
`SETTINGS_MAX_CONCURRENT_STREAMS`，每个响应 body 最多缓冲 1 MiB，整批成功后
物理连接才会归池。默认 header 和 CookieStore 会被消费，第一批收到的 Cookie
可用于下一批。

这个 batch API 不支持 TLS、streamed response、任意独立 lease、retry/redirect
重放和逐请求 cancellation。配置 request、observe 或 transport-touchpoint hook
时会在联网前拒绝；不要把 response 顺序返回误解为服务端串行执行。

需要让独立调用方在同一个连接内分别持有 response lease 时，可以显式打开
cleartext multiplex session：

```cangjie
let session = client.openNativeH2Session(
    "http://127.0.0.1:8080",
    maxConcurrentStreams: 8
)
try {
    let first = spawn {
        session.send(
            NativeH2BatchRequest("POST", "/slow")
                .header("content-type", "text/plain")
                .bodyString("buffered payload")
        )
    }
    let second = spawn {
        session.send(NativeH2BatchRequest("GET", "/fast"))
    }

    let streamed = spawn {
        session.send(
            NativeH2BatchRequest("POST", "/upload")
                .bodyStream(input, exactLength)
        )
    }

    let fastResponse = second.get(Duration.second * 5)
    println(fastResponse.body())
    let slowResponse = first.get(Duration.second * 5)
    println(slowResponse.body())
    println(streamed.get(Duration.second * 5).body())
} finally {
    session.close()
    client.close()
}
```

`NativeH2Session` 仍是显式 Preview：只接受同一 `http://` origin；request body
可以是 buffered bytes/string、通过 `bodyStream(input, exactLength)` 提供的精确
长度 one-pass `InputStream`，或通过 `bodyStream(input)` 提供的未知长度 source。
精确长度 source 缺少 `content-length` 时由 session 自动补齐；未知长度 source
不发送该 header。stream 由调用方持有且不会重放，producer 每次最多读取 8 KiB、每 stream 最多
预取 32 KiB，读取用户 `InputStream` 时不持有 session-state 或 writer mutex。
Ignite 不会关闭该 stream；取消会在一次 `read` 返回后生效，因此可能阻塞的 source
必须由调用方提供可取消或有界超时的读取实现。
本地并发上限最多 32 且会继续服从对端
`SETTINGS_MAX_CONCURRENT_STREAMS`。连接只有一个 frame reader；request DATA
同时服从 connection/stream send window，并在收到 `WINDOW_UPDATE` 或
`SETTINGS_INITIAL_WINDOW_SIZE` 变化后继续推进。每个 stream 最多保留 65,535
字节未读 response body，connection-level WINDOW_UPDATE 独立推进，所以一个慢
stream 不会仅因占满自己的窗口而阻塞兄弟 stream。完整读到 EOF 后 session
可以归还连接；提前 `close()` 某个 response 会发送 `RST_STREAM CANCEL`，已打开
的兄弟 stream 可以继续。若对应 request body 尚未发完，该物理连接会进入
retiring，避免在未知 peer 消费状态下复用。`RestClient.close()` 会兜底关闭遗忘
的 session。`NativeH2BatchRequest.deadline(Duration)` 会把超时限制在单个
stream，并保留兄弟 stream 与共享物理连接。

cleartext 入口不负责 TLS；同一套 multiplex runtime 也可由下方的
`openNativeTlsH2Session(...)` 接入 Native TLS。两种 session 都支持
`NativeH2BatchRequest.deadline(Duration)` 的逐 stream CANCEL，但不支持自动
RequestBuilder H2 streaming、retry/redirect 重放或 priority；配置 request、observe
或 transport-touchpoint hook 时会 fail closed。
它提供的是有界独立 lease，不代表任意生产级 H2 调度已经完成。

需要在 TLS1.3 + `h2` ALPN 上持有并发 stream lease 时，使用显式 TLS session：

```cangjie
let client = RestClient(poolSize: 4)
    .allowExperimentalTransport()
    .preferTransportBackend("ignite-native-h2-client")
    .useNativeTls(NativeTls13ClientConfig(
        trustAnchorsPemBundle,
        "api.example.com",
        alpnProtocols: ["h2"]
    ))

let session = client.openNativeTlsH2Session(
    "https://api.example.com",
    maxConcurrentStreams: 8
)
try {
    let first = spawn { session.send(NativeH2BatchRequest("GET", "/a")) }
    let second = spawn { session.send(NativeH2BatchRequest("GET", "/b")) }
    println(first.get(Duration.second * 5).body())
    println(second.get(Duration.second * 5).body())
} finally {
    session.close()
    client.close()
}
```

`NativeTlsH2Session` 只接受所打开的同一 `https://` origin，并复用 cleartext
session 的流控、乱序响应归属和 one-pass request stream 语义。所有 response
完整结束后，连接可回到同 trust policy 的 TLS H2 pool；session 关闭时仍有活跃、
取消或未完成 stream，则物理连接会被淘汰。它不自动读取系统 CA，也不提供 replay、
redirect retry 或 priority；`NativeH2BatchRequest.deadline(Duration)` 仍可对单个
stream 发送 `RST_STREAM(CANCEL)`。

显式 Native TLS1.3 H1/H2 client 连接池提供有界 idle 生命周期和快照：

```cangjie
let client = RestClient(poolSize: 10)
    .nativeTlsIdleTimeout(Duration.second * 30)
    .preferTransportBackend("ignite-native-h2-client")
    .useNativeTls(NativeTls13ClientConfig(
        trustAnchorsPemBundle,
        "api.example.com",
        alpnProtocols: ["h2"]
    ))

let response = client.get("https://api.example.com/data")
let body = response.body()
let snapshot = client.nativeTlsRuntimeSnapshot()
println(snapshot.toJson())
client.close()
```

`nativeTlsIdleTimeout(...)` 必须为正数，默认是 `30s`。修改策略会在原有
H1/H2 pool 上更新上限并关闭当前 idle Native TLS 连接，因此在途 response
仍归还给同一个 owner，且会遵循新策略。快照分别提供 H1/H2
的 idle、opened、reused、returned、retired、expired 计数；它是进程内累计
生命周期事实，不是吞吐 benchmark。连接完整消费后才归池，超过 idle 上限、
本地已关闭、提前关闭 response、协议错误或 `RestClient.close()` 都会淘汰连接。

上面的低层 socket API 都由调用方持有 `TcpSocket`：

- 调用方负责 connect 或 accept。
- 调用方负责 TLS、ALPN 和证书策略。
- 调用方负责设置 socket timeout。
- `finish()` 只发送 `NO_ERROR GOAWAY`，物理 socket close 仍由调用方负责。
- 低层批量 API 和 `RestClient.sendNativeH2Batch(...)` 的请求/响应 body 仍是有界内存数组；普通显式 `RestClient` backend 支持单 lease 增量 response，`openNativeH2Session(...)` / `openNativeTlsH2Session(...)` 支持 buffered body、精确或未知长度 one-pass request stream、并发 response lease 与逐 stream deadline CANCEL，但自动重放、priority 和任意生产级调度尚未提供。

`NativeH2ConnectionControl.requestClose()` 可请求 server connection 发出 `NO_ERROR GOAWAY`。协议错误会使用对应的 protocol、flow-control、frame-size 或 compression error code。

### HPACK / Huffman 边界

当前 Native H2 主实现支持静态表、有界动态表、indexed/literal/table-size
update、RFC 7541 Appendix B 的 257 项 Huffman code table、EOS/padding 校验和
完整 256-octet symbol 覆盖；解码后的公开 `String` 仍要求合法 UTF-8。Outbound
仅在 Huffman 结果更短时启用，并对敏感 Header 使用 never-index；重复 ordinary
Header 可进入 connection-owned dynamic table。

Jingui accepted-transport compatibility parser 仍不是同一条完整 HPACK 路径，
而现有 byte profile 只证明重复 Header 的编码形态，不代表所有负载的吞吐收益。
动态 Zstd/Brotli 所缺的 Huffman 属于压缩算法熵编码，是另一项能力。
